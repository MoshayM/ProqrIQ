1. What is ProqrIQ?

ProqrIQ is a B2B cost engineering and quotation platform built specifically for Pepperl+Fuchs (P+F) engineers. The name comes from "ProQR IQ" — professional quotation intelligence.

In simple terms: an engineer uploads a part drawing, the AI reads it, queries your internal engineering documents (the Knowledge Base), and produces a detailed cost breakdown — materials, machining time, labour, overhead, and margin — with a confidence score. If the AI is not sure enough (below 70%), it asks clarifying questions instead of guessing.

The platform then goes further:

  • Bulk Costing — cost up to 50 parts at once, running in parallel
  • Assembly BOM — build a Bill of Materials tree, cost every child part, and roll up the total automatically
  • Supplier Sourcing — AI discovers suppliers, you import their quotes, the app compares them against your should-cost, and generates a negotiation report
  • Approval Workflow — submitted quotes route to the CEO for approval; approved quotes are permanently locked with a full audit trail
  • Subscription Plans — Free, Pro (€79/month), and Organization (€249/month) tiers gate features and control who can do what
On-Premise by Design: The entire application runs on your own server. Your drawing files, cost data, and engineering documents never leave your infrastructure (except when the AI analyses content — that goes to Anthropic/Groq/etc. which are governed by their own data agreements).

4. Phase 0 — Project Foundation & Infrastructure

Initial commit: e69c2f1

Phase 0 Starting from Zero — Building the Foundation

What happened

The project started as an empty folder. Everything had to be created from scratch — the database structure, the server, the frontend, and a way to get it live on the internet.

What was built

  • Project structure: Two separate codebases — client/ (browser app) and server/ (API server) — sharing TypeScript types through a shared/ folder
  • Database schema: SQLite database with tables for users, quotations, cost lines, materials, cycle time steps, knowledge-base documents, audit logs, and more
  • JWT authentication: Secure login system using JSON Web Tokens — users log in, get a token, and every request proves identity with that token
  • Role system: Five roles built in — engineer, cost_analyst, procurement, ceo, admin — each with different permissions
  • Passkey (WebAuthn) authentication: Phishing-resistant sign-in using your device's fingerprint/face unlock — no password needed
  • Vercel deployment: Connected to the GitHub repository so every code push automatically deploys to proqriq.vercel.app
  • Initial database migration to Turso: Early attempt at a cloud database (later reverted to on-premise SQLite)
Why passkeys? Traditional passwords can be phished (stolen through fake login pages). A passkey is a cryptographic key stored on your device — it physically cannot be stolen via a phishing email. This was added as a premium security feature early in development.

6. Phase 2 — AI Router, Supplier Map & Billing System

Commits: 7547f7f through 9c413e8

Phase 2 The Big Three — AI Intelligence, Supplier Power, and Monetisation

AI Router (Feature 3)

This was a major architectural upgrade. Instead of always sending AI requests to one provider (Anthropic), the AI Router intelligently directs different tasks to different AI models based on cost, speed, and capability:

  • Each type of task (drawing analysis, cost estimate, supplier suggestion, KB search, negotiation) can be assigned a different AI provider
  • Admins manage this through the AI Control page — no code changes needed
  • The system logs every AI call: which model, how many tokens, what it cost, success/failure
  • A "Savings vs all-Sonnet" KPI shows admins exactly how much money the routing is saving
  • Exponential backoff retry: if an AI provider is temporarily busy, the system waits and retries automatically (1s → 2s → 4s → 8s) before showing an error
  • Dynamic routing: changing the AI provider in admin settings takes effect immediately — no restart needed

Complete Supplier Map (Feature 4)

The Supplier Map is a full supplier relationship management module built into the app. It has three panels:

PanelWhat it shows
Left — Filter sidebarFilter by country, capability, minimum tier rating, keyword search
Centre — Map + ListInteractive map showing supplier locations with pins; switchable to list view. Fullscreen mode. Resizable map.
Right — Detail panelFull supplier profile, contact info, and 5 sub-tabs

The 5 supplier detail tabs:

  • Info: Company profile, capabilities, certifications, contact details
  • Quotes: All supplier quotes for this supplier — add manually or AI-extract from a PDF/email
  • Compare: Apple-to-apple comparison against your should-cost — material, machining, overhead, profit margin — with ±15% divergence flags. The maths is deterministic; AI never touches the numbers.
  • Negotiate: AI-generated negotiation talking points and a recommended target price (never below your should-cost). AI email draft composer built in.
  • Customers: Which of your internal parts this supplier has been used for — donut chart + table
Key principle — deterministic comparison: The price gaps, delta calculations, and divergence flags are all pure maths — no AI involved. AI is used only to phrase the talking points. This means the comparison numbers are 100% auditable and reproducible.

Three subscription tiers were built with hard feature gates:

Technical implementation:

8. Phase 4 — Payment Gateway Integration

Commits: 63d5407 through bb801a6

Phase 4 Taking Real Money — Payment Processing

What was built

Two payment gateways were integrated simultaneously so the system has a fallback:

  • Razorpay (primary) — covers India and international markets with UPI, cards, net banking
  • Stripe (secondary) — covers Europe and US with cards, SEPA, wallets

The Checkout Flow

  1. User selects a plan (Pro or Organization) and billing cycle (monthly/annual)
  2. They click "Subscribe" — the server creates an order with Razorpay
  3. Razorpay's hosted payment UI opens (UPI shown first as the preferred method)
  4. After successful payment, Razorpay sends a webhook to the server
  5. The server verifies the webhook signature (cryptographic proof it's real), updates the subscription in the database, and the user's plan activates immediately
  6. Confetti fires; the user sees their new plan badge

Webhook Security

Payment webhooks are cryptographically signed by Razorpay. Our server verifies the signature before processing any subscription change — a forged or tampered request returns a 400 error and is ignored. This prevents attackers from sending fake "payment successful" messages.

Pricing Quiz

A 3-question quiz on the /pricing page helps users choose the right plan — "How many people will use this?", "Do you need bulk costing?", "Do you manage suppliers?" — before showing them the pricing cards.

Payment UX Fix

A post-launch bug was found where the Razorpay payment window was closing before the confirmation could be shown. This was fixed by changing the trigger from onDismiss to onSuccess to ensure the success state is shown correctly.

9. Phase 5 — Multi-AI Provider Expansion

Commits: f14243f through aa46959

Phase 5 Never Pay More Than You Have To — Multiple AI Brains

Why multiple AI providers?

Anthropic's Claude is the gold standard for complex reasoning but has costs per API call. For simpler tasks (summarisation, basic costing, supplier lookup), cheaper or even free alternatives can produce acceptable results. Building a router means you can use the cheapest model that still gets the job done.

Providers Added

ProviderModelCostBest for
Anthropic (Claude)claude-sonnet-4-20250514PaidComplex costing, drawing analysis, highest accuracy
GroqLlama 3.3 70B, Llama 3.1 8BFree tierFast responses, basic tasks, development/testing
Together AIMultiple open-weight modelsLow costMid-complexity tasks at reduced cost
xAI Grokgrok-2-vision-1212PaidVision (drawing analysis) with Grok capability
Ollama (Local)Any open-weight modelFreeCompletely air-gapped, no external calls

Smart Fallback System

If the primary AI provider fails or is busy, the system automatically tries the next configured provider — no error shows to the user unless every configured provider fails. The fallback order is configurable by admins in the AI Control panel.

Admin Key Management UI

Admins can enter, test, remove, and toggle API keys for each provider directly in the AI Control page — no server restarts, no environment variable editing required.

Groq as Primary (Cost Saving Move)

After the Anthropic API credits were exhausted during development, the routing was switched so that Groq's free tier became the primary provider. The Groq free tier gives 6,000 tokens per minute — enough for most costing tasks at zero cost. Anthropic remains available as a premium option when highest accuracy is needed.

Rate Limit Handling: Groq's free tier has a rate limit. When it's hit, the server automatically waits 65 seconds and retries — up to 3 attempts — before returning an error. This means most rate-limit hits are invisible to the user; they just experience a slight delay.

Security: OWASP Top 10

The OWASP Top 10 is the industry-standard list of the 10 most common and dangerous web security vulnerabilities. All 10 were tested:

  • SQL Injection — all database queries use parameterised statements, never string concatenation
  • Broken Authentication — JWT validation on every route, passkey support
  • Sensitive Data Exposure — API keys server-side only, passwords hashed with bcrypt
  • Cross-Site Scripting (XSS) — React's automatic escaping + Content Security Policy headers
  • Broken Access Control — role check middleware on every route
  • Security Misconfiguration — CORS restricted to allowed origins, debug mode off in production
  • Insecure Deserialization — all AI JSON responses go through parseAIJSON() safety wrapper
  • Using Components with Known Vulnerabilities — automated npm audit in CI pipeline
  • Insufficient Logging — every mutation logged to audit table
  • Server-Side Request Forgery (SSRF) — supplier lookup allow-list prevents calling arbitrary URLs

CI/CD Security Pipeline (GitHub Actions)

Three automated security checks run on every code push:

  • CodeQL SAST: Static analysis — reads the code looking for security bugs (SQL injection patterns, XSS risks, etc.)
  • npm audit: Checks every dependency for known CVEs (security vulnerabilities)
  • OWASP test suite: Runs the OWASP checks described above automatically

Data Scoping

Engineers can only see their own quotes and batches — not each other's. CEOs and Admins see everything. This was implemented at the database query level, not just the UI — a logged-in engineer cannot retrieve another engineer's quote even by guessing the URL/ID.

17. Phase 8 — AI Quality Hardening, Bug Fixes & Routing Overhaul

Commits: a22b7c8 through 854528b

Phase 8 Hardening the AI Pipeline — Making Every Call Smarter, Cheaper, and Crash-Proof

Background — why this phase was needed

After Phase 7 shipped, an engineer reported that "AI processing failed — please try again" appeared whenever a part drawing was uploaded for analysis. Separately, the help panel was visually disappearing behind page content. Both issues were diagnosed and fixed — and while fixing the drawing analysis root cause, the team conducted a full audit of every AI call in the application. That audit identified six additional improvements that were implemented in the same session.

Bug Fix 1 — Help Panel Hidden Behind Page Content

What the user saw

Clicking the help button (bottom-right) opened the panel, but it appeared hidden behind the main content area instead of floating on top.

Root cause (technical)

Modern CSS has a concept called a stacking context. When an element uses an animation that transitions its opacity from 0 to 1 (as Framer Motion does for page transitions), the browser creates a new stacking context for that element. Any child element — even with a high z-index value — cannot appear above its stacking context parent. The help panel was a child of the animated page wrapper, so no matter what z-index number it had, the browser kept it behind the animated parent.

Fix applied

  • Help button: z-index raised to 100000
  • Help panel: z-index raised to 99999, and moved so it renders outside the animation stacking context
  • Panel height clamped to min(560px, 100vh − 108px) so it never overflows short screens
Result: The help panel now always floats cleanly above all other content on every screen, including modals and the bulk progress bars.

Bug Fix 2 — Drawing Analysis Crash ("AI processing failed")

What the user saw

Uploading a part drawing (PNG, JPG, PDF, or STEP/IGES 3D file) and clicking "Analyse" returned the error message: "AI processing failed — please try again." This happened consistently when the application was configured to use Groq as the AI provider.

Root cause A — source_tier validation crash

Every cost line the AI produces must include a source tier number (1–5) that indicates how reliable the figure is. The validation code was written to throw a hard error if the AI returned a missing or invalid tier number. Groq's Llama 3.3 70B model frequently returned null for this field. The thrown error had no HTTP status code, so the error classifier fell through to a generic 500 response — producing the unhelpful "AI processing failed" message.

Fix for root cause A

Replaced the hard-throwing validateSourceTier() function with a forgiving coerceSourceTier() function. Instead of crashing, it logs a warning and defaults to tier 5 (meaning "AI assumption — treat with caution"). The cost estimate is still returned; the user sees the data, and the lower confidence tier is recorded for traceability.

Root cause B — Groq silently dropping image data

When a PNG/JPG/PDF drawing was uploaded, the system routed the analysis to Groq. However, Groq's free-tier models do not support vision (they cannot read images). Groq simply ignored the image and answered based on text context alone, producing garbage or null values — which then failed validation and triggered the crash.

Why this was silent: Groq did not return an error. It just pretended it had read the drawing when it hadn't. The application had no way to know the image was silently dropped.

Fix for root cause B

Added a requiresVision: true flag to the drawing analysis function. When this flag is set, the AI Router checks whether the selected provider can handle images. If not, it automatically switches to the first active vision-capable provider (Anthropic Claude, OpenAI GPT-4o, Google Gemini, or xAI Grok). A new VISION_FALLBACK_MODEL table maps each provider to its confirmed vision-capable model — for example, Anthropic switches to claude-sonnet-4-20250514, not Haiku (which also lacks vision support).

Result: Drawing analysis now always uses a vision-capable model. If the cheapest provider (Groq) is selected and it can't see images, the router silently upgrades to Anthropic Sonnet for that specific call, then returns to Groq for non-vision tasks.

Improvement — "Best by AI Principle" Routing Overhaul

The principle

The goal: maximum accuracy at minimum cost. Not every AI task needs the most powerful (and expensive) model. A simple email draft does not require the same model as a precision cost estimate. The routing overhaul defines two clear tiers and maps every task in the application to the right one.

TierModel chainWhen it's used
Quality tier Groq 70B (free) → Anthropic Sonnet (paid fallback) Tasks where an incorrect answer costs more than the model call — costing, assembly roll-up, supplier extraction, negotiation talking points
Fast tier Groq 8B (free) → Anthropic Haiku (paid fallback) Tasks where speed and cheapness matter more — supplier discovery, KB summarisation, quote Q&A, email drafts, help chat
